# 设计

## 请求结构配平

- 配平放在唯一的请求出口 `RequestBuilder.Build`，四种协议共用同一份消息副本，因此不存在「某条协议漏配」的分支。
- 判据是「结果必须紧跟调用」：只看助手消息之后连续的一段工具消息，按 `tool_call_id` 配对；没有标识的协议（Gemini、部分自建代理）退回按工具名配对。
- 两条分支（全部配上、部分配上）走同一套逐条 `matched[]` 放行逻辑。此前的缺陷正是两条分支行为不一致：「全部配上」直接整段放行，最常走的那条反而没有设防。
- 修复只产出复制件。面板的操作卡片与撤销按钮按原对象登记，就地改写会让记录与界面各说一套。
- 整条调用都不成立且正文为空时补一句说明，因为 Anthropic 不接受空的 assistant content。

## 未声明工具时的历史降级

- `IncludeTools` 为假表示这次请求体里没有 `tools` 声明。严格网关见到「有工具消息却没声明 tools」会整轮拒绝，因此需要在出口把痕迹降级。
- 助手调用并进正文（保留工具名与参数），工具结果改写成普通用户文本，并保留工具结果身份标记——上下文压缩靠它优先压这一类。
- 不直接删除工具消息：模型会失去「自己做过什么、拿到了什么」，下一步必然重复同一批读取。
- 降级后的正文刻意避开 `tool_calls`/`function_call`/`tool_use` 这些字面量，否则等于把要躲开的痕迹又带回去。
- 没有痕迹时原样交出列表，不做多余复制。

## 参数校验宽容度

- 校验层与执行层必须同口径。执行层读的是 `Value<long?>`、`OptionalBool` 这类宽松取值，校验层按 `JTokenType` 严格比对就会「校验比执行更严」：模型换个等价写法就被拒，而错误信息说「必须为 integer」又与工具实际行为不符。
- 非必填参数的 `null` 视为未提供；必填里的 `null` 与全空白字符串仍报 `ARG_MISSING`。
- `integer`/`number`/`boolean` 接受可无损转换的字符串。无损是硬要求：`12.0` 读成整数不丢信息，按整数放行；`12.5` 会丢小数，仍拒绝。
- 数组与对象不放宽：它们没有无歧义的字符串形态，放行只会把错误推迟到更深的地方。
- 错误信息带上实际取值（字符串带内容并截断），模型才知道错在哪。
- schema 里可空的布尔参数统一声明为 `["boolean","null"]`，让目录文本、schema、校验与执行四处一致。

## excel_object 的校验顺序

- `root` 缺失要弹一次「选哪一层」，那是一次真实的用户交互。把非交互就能判定的必填与类型检查提前到交互之前，模型漏写 `path` 之类的参数立刻收到 `ARG_MISSING`，不惊动用户。
- 用带跳过集合的校验重载跳过 `root`，其余参数照常检查。
- 用户选择后写回 `args["root"]`，再做一次完整校验。这一遍是审批前的最后一道，必须面对完整的参数。
- 缺参判定抽成一个助手方法，与校验层同一口径，避免「校验说缺、执行却当有」。

## 版本与仓库卫生

- 版本号散落在程序集元数据、面板回退版本与版本测试三处，任何一处漏改都会让测试或发布说明说谎，因此三处必须同一提交内一起改。
- 面板的版本断言改为读页面自身的 `data-version` 再与文本比对：断言的是页面一致性，而不是「这台机器上装的是不是当年那个版本」。
- 仓库根的运行期残留来自子进程把字面量或相对路径当成「当前目录下的名字」，全部纳入忽略规则，并逐条写明成因，否则下一个人仍会把它们重建出来。

## 验证

- 统一入口 `scripts/verify-all.ps1` 串起构建、四组 .NET 测试与全部 web 用例，任一步非零即整体失败，末尾汇总「通过/失败/跳过」并逐条指向日志。
- web 用例数按目录实际文件数统计，不写死数量。
- 新增回归覆盖：孤儿结果配平、参数宽容度的双向用例、四种协议的工具痕迹降级、历史对象未被改写。
